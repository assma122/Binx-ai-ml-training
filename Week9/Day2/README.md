# Week 09 — Day 02  
## Serving the IMDb Sentiment Model with FastAPI

This project demonstrates how to transform a trained Machine Learning model into a usable REST API using **FastAPI**.

The IMDb sentiment model developed previously is loaded together with its fitted **TF-IDF vectorizer**, then exposed through an API that accepts movie reviews and returns sentiment predictions.

The service also includes:

- Input validation with **Pydantic**
- Reuse of the original training preprocessing pipeline
- A `POST /predict` prediction endpoint
- Prediction confidence scores
- A `GET /health` monitoring endpoint
- Interactive API testing through Swagger `/docs`
- Validation testing for invalid requests

---

## Project Objective

The goal of Day 2 is to move the trained IMDb sentiment classifier beyond the notebook environment and expose it as a reusable API service.

The final workflow is:

```text
Movie Review
      ↓
Pydantic Validation
      ↓
Text Preprocessing
      ↓
Saved TF-IDF Vectorizer
      ↓
Logistic Regression Model
      ↓
Prediction + Confidence
      ↓
JSON Response
```

This allows a website, mobile application, or backend system to send a movie review and receive a sentiment prediction through an HTTP request.

# Why Reuse the Saved Vectorizer?

The model was trained using features generated by a specific fitted TF-IDF vectorizer.

Therefore, new movie reviews must be transformed using the **same vectorizer**.

Creating or fitting a new TF-IDF vectorizer during deployment could change the feature representation and create inconsistencies between training and prediction.

The correct serving workflow is:

```text
New Review
    ↓
Same Preprocessing
    ↓
Saved TF-IDF Vectorizer
    ↓
Trained Model
```

---

# Text Preprocessing

The API reuses the same text preprocessing logic used during model training.

The preprocessing pipeline includes:

- HTML entity decoding
- HTML tag removal
- Contraction handling
- Lowercasing
- Number removal
- Special-character cleanup
- Extra-space normalization
- Tokenization
- Stop-word removal
- Negation preservation
- POS tagging
- WordNet lemmatization

Negation words are intentionally preserved:

```python
{"not", "no", "nor"}
```

This is important because negation can completely change the meaning of sentiment.

For example:

```text
good
```

and

```text
not good
```

should not be treated as having the same sentiment.

# Loading the Saved Model and Vectorizer

The FastAPI application loads the saved artifacts from the previous day.

```python
from pathlib import Path
import joblib

BASE_DIR = Path(__file__).resolve().parent
DAY1_DIR = BASE_DIR.parent / "Day1"

MODEL_PATH = DAY1_DIR / "model.joblib"
VECTORIZER_PATH = DAY1_DIR / "vectorizer.joblib"

model = joblib.load(MODEL_PATH)
vectorizer = joblib.load(VECTORIZER_PATH)
```

Using `Path(__file__)` makes the paths more reliable because they are constructed relative to the location of `main.py`.

# Pydantic Input Validation

The API expects one field:

```text
review
```

The request schema is defined using Pydantic:

```python
class ReviewInput(BaseModel):
    review: str = Field(
        ...,
        min_length=3,
        max_length=5000
    )
```

This means that the review:

- Must be provided.
- Must be a string.
- Must contain at least **3 characters**.
- Must contain no more than **5000 characters**.

Pydantic validates the input before it reaches the Machine Learning pipeline.

This helps prevent malformed or invalid data from being passed to the model.

# Prediction Endpoint

The main prediction endpoint is:

```http
POST /predict
```

The endpoint performs the complete inference pipeline.

```python
@app.post("/predict")
def predict_sentiment(data: ReviewInput):

    cleaned_review = preprocess_review(data.review)

    review_vector = vectorizer.transform(
        [cleaned_review]
    )

    prediction = model.predict(
        review_vector
    )[0]

    probabilities = model.predict_proba(
        review_vector
    )[0]

    sentiment = (
        "Positive"
        if prediction == 1
        else "Negative"
    )

    confidence = float(
        probabilities.max()
    )

    return {
        "review": data.review,
        "prediction": sentiment,
        "confidence": round(confidence, 4)
    }
```

# Prediction Workflow

When a user sends a review to `/predict`, the API performs these steps:

### 1. Request Validation

Pydantic checks that the request contains a valid review.

```text
Incoming Request
        ↓
Pydantic Validation
```

### 2. Text Preprocessing

The movie review is cleaned using the same preprocessing pipeline used during training.

```text
Review
   ↓
preprocess_review()
```

### 3. TF-IDF Transformation

The processed review is transformed using the fitted vectorizer saved from Day 1.

```text
Cleaned Review
      ↓
Saved TF-IDF Vectorizer
```

### 4. Model Prediction

The generated feature vector is passed to the Logistic Regression model.

```text
TF-IDF Features
      ↓
Logistic Regression
```

### 5. Confidence Calculation

The model probability output is obtained using:

```python
model.predict_proba()
```

The highest probability is used as the confidence score.

### 6. JSON Response

FastAPI returns the prediction together with the confidence score.

```json
{
  "review": "...",
  "prediction": "Positive",
  "confidence": 0.9813
}
```

# Why Pydantic Validation Matters

Machine Learning APIs should never assume that incoming user data is valid.

Without validation, malformed requests could:

- Cause preprocessing errors.
- Produce unexpected behavior.
- Send incorrect data into the model.
- Make the service less reliable.

Pydantic acts as a validation layer between the client and the prediction pipeline.

```text
Client
  ↓
Pydantic Validation
  ↓
Valid Data
  ↓
Machine Learning Pipeline
```

# Training vs Serving

During training, the model learns patterns from historical IMDb reviews.

```text
Training Dataset
      ↓
Preprocessing
      ↓
TF-IDF Fit
      ↓
Logistic Regression Training
      ↓
Save Artifacts
```

During serving, the saved components are reused.

```text
New User Review
      ↓
Validation
      ↓
Same Preprocessing
      ↓
Saved TF-IDF Transform
      ↓
Saved Logistic Regression
      ↓
Prediction
```

The vectorizer and model are **loaded**, not retrained.

---

# Training–Serving Consistency

One of the most important parts of model deployment is ensuring that inference data is processed in the same way as training data.

In this project, the API reuses:

- The same text-cleaning rules
- The same stop-word configuration
- The same negation handling
- The same lemmatization logic
- The same fitted TF-IDF vectorizer
- The same Logistic Regression model

This reduces the risk of **training-serving skew**.
